# Master Requirements Specification

## Composed native Quire language standard

## 1. Purpose

This root indexes the native Quire language requirements. Complete V1 is the
entire language, runtime, analysis, backend, tooling and
qualification system under one editable source authority. The existing
finite-state implementation is a development slice, not the product boundary.
The [subsystem index](subsystems/index.md) and AD-001 through AD-011 organize the
complete architecture. Draft specifications and reviews do not establish
implemented capabilities.

## 2. Scope

### 2.1 In Scope

FS01 native grammar and composed profile architecture; FS02 shared model/source and artifact identity; FS03 state semantics; FS04 temporal, clock and observation contracts; the native choreography/protocol and compensation profile; FS05 strict interchange and migration; FS06 output mapping and loss contracts. The [atomic V1 inventory](../docs/v1-capability-inventory.md) is the scope authority. The older [51-group matrix](../proposals/quire-v1/capabilities.md) is a historical crosswalk and cannot defer or combine away atomic work.

FS06 accepts the [output-mapping subsystem](assurance/AD-004-output-mapping-subsystem.md),
common request/record/package contract and bounded OCL 2.4, SysML 2.0/KerML
1.0 and FRETish 3.1 profiles. Qcir #95 / PR #98 implements the shared Rust
request/record/package foundation at `5ea7730`; target-specific executable
exporters are implementation-plan work governed by the complete-V1 contracts,
not omitted language scope.

### 2.2 Out of Scope

B's portable method/plan/result implementation, quire-rs extraction, the FCD
extraction-frontend lift,
workflow adapters and other consuming engines are cross-repository delivery
owners rather than production code owned by this specification repository.
Local projection, realizability, relational analysis, model testing and workflow
driving are complete V1 capabilities with their own typed subsystem boundaries.
Domain declarations outside spec artifacts, a foreign editable source frontend and automatic
public publication remain integrity or operational boundaries. External OCL,
FRETish and SysML/KerML forms are output mappings, not editable source
frontends.

## 3. System Overview

### 3.1 System Description

The language links complete values/models/expressions, temporal properties,
dynamic choreography and verification plans through common typed identities,
with explicit semantic profiles and specialized representations/evaluators. The
native pipeline preserves source identity through lossless parsing, model
linking, checking, execution, monitoring, analysis, exact lowering, tooling and
evidence intake. Schema packages, runtime populations, observations, backend
runs and qualification decisions remain distinct subjects.

### 3.2 Intended Users

Specification authors, verification operators and toolchain integrators.

## 4. Requirements Architecture

Each stakeholder requirement, story, functional requirement, quality constraint and integration specification is a separate catalog-typed file. Proposal documents remain detailed design inputs; this index does not replace those requirements.

## 5. Requirement Classes

StR states the operational need. US records user intent. FR defines observable behavior. NFR records measurable quality constraints. IT specifies a real external process/API/file boundary. TC and matrix coverage are assessed by the review workflow.

## 6. Requirement Identification

IDs are stable within this repository. Cross-repository identities use ix://agent-ix/quire-specification/ID. Acceptance criteria use the parent ID plus -AC-N; integration steps use -SC-NN.

## 7. Requirement Quality Policy

Requirements use atomic observable outcomes. Unknown support, absent evidence and unimplemented prerequisites remain explicit. Validation of Markdown structure cannot establish semantic correctness or implementation completion.

## 8. State and Execution Model

### 8.1 State Semantics

Runtime inputs are immutable typed finite populations with explicit closure assumptions. Object identity differs from record equality. Optional absence, invalid input and unavailable observation retain distinct meanings.

### 8.2 Transition Semantics

Operation observations belong to one invocation with an authored frame and exact object delta. The required v1 choreography profile composes those contracts with roles, typed messages, choices, parallel branches, bounded repetition and compensation. Its temporal and observation contracts define clocks, captured values, progress and completeness separately from state snapshots.

### 8.3 Determinism Guarantees

Guard and collection evaluation order, source activation and selected canonical domains remain explicit. Resource exhaustion yields incompleteness, not a logical violation.

## 9. Events and Signals

### 9.1 Event Model

The v1 observation contract distinguishes typed domain events, role instances, messages, correlation, clocks, causal ordering and progress. State snapshots and operation captures bind explicitly to those observations. A specification evaluator consumes the records; it does not execute business actions or introduce an application event bus.

### 9.2 Event Guarantees

Only events established by the selected observation binding contribute facts. Closed execution, an open prefix and an incomplete file have different meanings. Incremental monitoring receives explicit progress so silence can discharge or violate a deadline only when the required interval is observable. Missing probes or valuations remain unavailable evidence.

## 10. Error and Failure Model

### 10.1 Error Classification

Invalid syntax/input and unsupported capabilities refuse their stage. Missing observations, cancellation and exhausted resources remain incomplete.

### 10.2 Failure Handling Guarantees

No failed prerequisite yields a completed Boolean. No unsupported obligation is silently erased.

## 11. Traceability

Frontmatter relates StR, US, FR/NFR and IT artifacts. Acceptance-criterion-to-TC coverage and implementation trace tags require the review workflow; existing Rust tests do not automatically create formal TC identities.

## 12. Verification Strategy

Run Quire over this exact repository scope. Use real implementations and independent expected cases for integration evidence. Quire v1 acceptance includes the state workflow, timed refund and branching compensated choreography through executable evaluation, replay and incremental monitoring. An observed pass does not itself qualify the system. Existing state tests and authored examples establish only their stated subset.

## 13. Change Management

Specification changes are reviewed with `/spec-review` before implementation
that depends on them.

## 14. Lifecycle Status

The 2026-09-09 ruling selects native Quire as the sole editable formal-clause
language. FS01's accepted [language charter](assurance/AD-003-native-quire-language-charter.md)
fixes the `ix:native` identity, composed profile hierarchy and language/profile/
backend separation. [FR-019](functional/foundation/FR-019-admit-native-source-profile.md)
and the [superseded amendment](../proposals/native-source-1-draft/README.md) carry
forward its admission rules. The old `state-finite/1-draft` candidate is not
enabled or aliased; adopted historical definitions and their implementation
remain distinguishable from composed semantic candidates.

## 15. Governance Notes

Use owning issues and isolated worktrees. Preserve dependency/template grants.
Publication administration is operational governance and does not reduce
complete-V1 product scope. The complete composed grammar, assessment interfaces
and cross-subsystem boundaries are specified by AD-001 through AD-011, the
interfaces in the [subsystem index](subsystems/index.md) and the complete-V1
functional requirements.
