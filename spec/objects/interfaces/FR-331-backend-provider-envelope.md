# FR-331: Backend provider request and result envelope

## Description

When a contract package is submitted to a backend provider, the producer SHALL use the immutable BackendProviderEnvelope contract below rather than an untyped map, display string or implementation-local structure.

## Properties

- `contract_version` — exactly `quire.backend-provider/v1`.
- `capability_vocabulary` — exactly `quire.capability-kind/v1`; it selects the FR-290 vocabulary for every kind in `manifest`, `request` and `results`.
- `manifest` — one backend descriptor per registered backend in the registry snapshot: backend identity, manifest digest, version, advertised (FR-290 kind, mode) pairs, domains, options, bounds, pinned tool identity and, where the backend declares one, its obligation-form set (FR-349). Backend identities are unique.
- `request` — contract-package items, requested claims, domains, limits and tool lock; for each item, its one required FR-290 kind, its extent and #222 extent classification (`bounded` or `unbounded`), the backend the caller names when it names one, and its `candidates`. The tool lock equals the pinned tool identity of each backend it routes to.
- `candidates` (per request item) — exactly one of: the set of candidates (backend identity, manifest digest) that the `quire-spec-language` registry computes under FR-290's candidate-set rule, ordered bytewise by identity and then digest; or the unknown-backend mark carrying the unregistered backend identity that the request named.
- `dispositions` — supported, requires-bound, unsupported or invalid-request per item.
- `artifacts` — immutable generated bytes with kind, identity and source map.
- `results` — proved, refuted, tested, inconclusive, unsupported, incomplete or failed per item. `unsupported` is recorded only for a supported, routed item whose pinned tool probe finds the tool missing or mismatched, errors or exceeds its limit; it names the capability kind, the backend and the expected and actual (or absent) tool identity.
- `counterexamples` — canonical assignments/traces plus originating run identity.
- `accounting` — exactly one terminal record for every requested item.

## Identity and validation

Request identity includes the capability vocabulary, manifest, package, claim/domain/bounds/options, each item's kind, extent classification, named backend and candidates, and the tool lock. Result identity includes artifacts, results and execution provenance.
Unknown contract versions, missing required properties, duplicate keys,
out-of-domain values, non-canonical encodings and a tool lock that differs from a routed backend's pinned tool identity refuse before consumption. A `capability_vocabulary` other than `quire.capability-kind/v1`, or none, refuses the envelope as `invalid_capability`/`unsupported-version`.

## Acceptance Criteria

| ID | Criteria | Verification |
| --- | --- | --- |
| FR-331-AC-1 | Negotiation completes before artifact emission. | Analysis |
| FR-331-AC-2 | An item settled `unsupported`, `requires-bound` or `invalid-request` emits no artifact; a tool-absence item keeps the artifacts it emitted before the probe, and they carry no verdict. | Analysis |
| FR-331-AC-3 | Every returned counterexample replays through the native owner with the same verdict. | Analysis |
| FR-331-AC-4 | `negotiate_*` settles each item from its `candidates` and extent classification under FR-290: unknown-backend, inconsistent candidates, an absent extent classification, and more than one candidate with no named backend settle `invalid-request`; an empty set settles `unsupported` with a warning naming the item's kind; a single candidate settles through its negotiation arm. A request item without `candidates` refuses before consumption. | Test (TC-271) |
| FR-331-AC-5 | Two requests whose items differ only in `candidates` have different request identities, and candidates serialize ordered by identity and then digest under every registration order. | Test (TC-271) |
| FR-331-AC-6 | A tool-absence `unsupported` result keeps the item's `supported` disposition, is the item's one terminal accounting record, and names the capability kind, backend and expected and actual tool identity. | Test (TC-271) |
| FR-331-AC-7 | An envelope whose `capability_vocabulary` is not exactly `quire.capability-kind/v1`, or is absent, refuses as `invalid_capability`/`unsupported-version` with none of its kinds read; a tool lock that differs from the routed backend's pinned tool identity refuses before consumption. | Test (TC-271) |
