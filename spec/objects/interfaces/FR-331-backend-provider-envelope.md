# FR-331: Backend provider request and result envelope

## Description

When a contract package is submitted to a backend provider, the producer SHALL use the immutable BackendProviderEnvelope contract below rather than an untyped map, display string or implementation-local structure.

## Properties

- `contract_version` — exactly `quire.backend-provider/v1`.
- `capability_vocabulary` — exactly `quire.capability-kind/v1`; it selects the FR-290 vocabulary for every kind in `manifest`, `request` and `results`.
- `manifest` — one backend descriptor per registered backend in the registry snapshot: backend identity, advertised (FR-290 kind, mode) pairs, domains, options, bounds and, where the backend declares one, its obligation-form set (FR-349). A backend that advertises `temporal-satisfaction` also carries its `fairness_kinds` ([FR-368](../../functional/temporal/FR-368-negotiate-temporal-model-check-items.md)). Backend identities are unique.
- `request` — contract-package items, requested claims, domains and limits; for each item, its one required FR-290 kind, its extent and #222 extent classification (`bounded` or `unbounded`), the backend the caller names when it names one, and its `candidates`.
- `temporal` (per `temporal-satisfaction` request item over a model subject) — the item's `subject` (initial-state references, universes, proof bounds), `item_kind` (`formula` or `deadlock-freedom`), resolved `fairness` set, `max_depth` for a bounded search and `limits`, as [FR-368](../../functional/temporal/FR-368-negotiate-temporal-model-check-items.md) states.
- `candidates` (per request item) — exactly one of: the set of candidate backend identities that the `quire-spec-language` registry computes under FR-290's candidate-set rule, ordered bytewise by identity; or the unknown-backend mark carrying the unregistered backend identity that the request named.
- `dispositions` — supported, requires-bound, unsupported or invalid-request per item.
- `artifacts` — immutable generated bytes with kind, identity and source map.
- `results` — proved, refuted, tested, inconclusive, unsupported, declined, incomplete or failed per item. `unsupported` is recorded for a supported, routed item whose tool probe finds the tool missing, errors or exceeds its limit, naming the capability kind and the backend; and, separately, for a supported item whose Kani run ends `Unavailable` (the solver or backend is absent after negotiation), naming the capability kind, the backend and the absent solver or backend identity. `declined` is recorded for a supported item whose Kani run ends `Refused`, `InvalidInput` or `IncompleteInput`, and names the typed refusal cause (QSL ADR-013 O-16 refusal category, QC-9); it keeps the item's `supported` disposition and is the item's one terminal accounting record, the same as a tool-absence `unsupported` result. A tool that becomes unavailable after a passing probe records `failed` with the same `tool-unavailable` cause. A Kani proof run whose obligation has zero SUCCESS checks records `inconclusive` with a typed vacuity cause, never `proved`; this is not a ninth result value (QSL ADR-013 FND-005, O-16 proof column).
- `counterexamples` — canonical assignments/traces plus originating run identity. A temporal refutation over a model subject is an [FR-364](../../functional/temporal/FR-364-replay-temporal-counterexamples.md) `TemporalCounterexample`. Each entry names exactly one of: the transcript's `artifacts` entry, whose assignments are its decode and are never separately stored, or the canonical assignments of a counterexample with no transcript; never both (QSL ADR-013 O-25, QC-6).
- `accounting` — exactly one terminal record for every requested item. A temporal item's terminal record carries its [FR-363](../../functional/temporal/FR-363-settle-every-behaviour-temporal-verdicts.md) proof basis and depth or cause, and any [FR-369](../../functional/temporal/FR-369-name-excluding-strong-fairness.md) `fairness.strong-would-exclude` warnings.

## Identity and validation

Request identity includes the capability vocabulary, manifest, package, claim/domain/bounds/options, each item's kind, extent classification, named backend and candidates, each temporal item's subject, item kind, fairness set, `max_depth` and `limits`. A different temporal horizon or budget can produce a different result, so a result is reused only for a request with the same request identity. Result identity includes artifacts and results.
Unknown contract versions, missing required properties, duplicate keys,
out-of-domain values and non-canonical encodings refuse before consumption. A `capability_vocabulary` other than `quire.capability-kind/v1`, or none, refuses the envelope as `invalid_capability`/`unsupported-version`.

## Acceptance Criteria

| ID | Criteria | Verification |
| --- | --- | --- |
| FR-331-AC-1 | Negotiation completes before artifact emission. | Analysis |
| FR-331-AC-2 | An item settled `unsupported`, `requires-bound` or `invalid-request` emits no artifact; a tool-absence item keeps the artifacts it emitted before the probe, and they carry no verdict. | Analysis |
| FR-331-AC-3 | Every returned counterexample replays through the native owner with the same verdict. | Analysis |
| FR-331-AC-4 | `negotiate_*` settles each item from its `candidates` and extent classification under FR-290: unknown-backend, inconsistent candidates, an absent extent classification, and more than one candidate with no named backend settle `invalid-request`; an empty set settles `unsupported` with a warning naming the item's kind; a single candidate settles through its negotiation arm. A request item without `candidates` refuses before consumption. | Test (TC-271) |
| FR-331-AC-5 | Two requests whose items differ only in `candidates` have different request identities, and candidates serialize ordered by identity under every registration order. | Test (TC-271) |
| FR-331-AC-6 | A tool-absence `unsupported` result keeps the item's `supported` disposition, is the item's one terminal accounting record, and names the capability kind and backend. | Test (TC-271) |
| FR-331-AC-7 | An envelope whose `capability_vocabulary` is not exactly `quire.capability-kind/v1`, or is absent, refuses as `invalid_capability`/`unsupported-version` with none of its kinds read. | Test (TC-271) |
| FR-331-AC-8 | A Kani proof run whose obligation has zero SUCCESS checks records the item's result as `inconclusive` with a typed vacuity cause, never as `proved`, and this cause is not a new result value. | Test (TC-274) |
| FR-331-AC-9 | A `counterexamples` entry names exactly one of the transcript's `artifacts` entry or the canonical assignments of a counterexample with no transcript, never both; a transcript-backed entry's assignments are its decode of that entry and are not separately stored. | Test (TC-275) |
| FR-331-AC-10 | A supported item whose Kani run ends `Refused`, `InvalidInput` or `IncompleteInput` records exactly one terminal result `declined` with a typed refusal cause; a supported item whose Kani run ends `Unavailable` records exactly one terminal result `unsupported` with a typed unavailability cause naming the capability kind, the backend and the absent solver or backend identity, not a tool identity. | Test (TC-276) |
| FR-331-AC-11 | A temporal item over a model subject carries `subject`, `item_kind`, `fairness`, `max_depth` for a bounded search and `limits`, and its terminal record carries its proof basis or cause; two requests differing only in `subject`, `item_kind`, `fairness`, `max_depth` or one `limits` member have different request identities, and a result recorded for one is not reused for the other. | Test (TC-302) |
