# FR-331: Backend provider request and result envelope

## Description

When a contract package is submitted to a backend provider, the producer SHALL use the immutable BackendProviderEnvelope contract below rather than an untyped map, display string or implementation-local structure.

## Properties

- `contract_version` — exactly `quire.backend-provider/v1`.
- `manifest` — provider identity, version, advertised (FR-290 kind, mode) pairs, domains, options, bounds and pinned tool identity.
- `request` — contract-package items, requested claims, domains, limits and tool lock; for each item, its required FR-290 kinds, its claim extent, the backend the caller names when it names one, and its `candidates`.
- `candidates` (per request item) — exactly one of: the set of registered backend identities that the `quire-spec-language` registry computes under FR-290's candidate-set rule, in ascending identity order; or the unknown-backend mark carrying the unregistered backend identity that the request named.
- `dispositions` — supported, requires-bound, unsupported or invalid-request per item.
- `artifacts` — immutable generated bytes with kind, identity and source map.
- `results` — proved, refuted, tested, inconclusive, unsupported, incomplete or failed per item. `unsupported` is recorded only for a supported, routed item whose pinned tool is missing or mismatched when probed before the run; it names the capability kind, the backend and the expected tool identity.
- `counterexamples` — canonical assignments/traces plus originating run identity.
- `accounting` — exactly one terminal record for every requested item.

## Identity and validation

Request identity includes manifest, package, claim/domain/bounds/options, each item's candidates and tool lock. Result identity includes artifacts, results and execution provenance.
Unknown contract versions, missing required properties, duplicate keys,
out-of-domain values and non-canonical encodings refuse before consumption.

## Acceptance Criteria

| ID | Criteria | Verification |
| --- | --- | --- |
| FR-331-AC-1 | Negotiation completes before artifact emission. | Analysis |
| FR-331-AC-2 | Unsupported or unbounded items emit no approximating artifact. | Analysis |
| FR-331-AC-3 | Every returned counterexample replays through the native owner with the same verdict. | Analysis |
| FR-331-AC-4 | `negotiate_*` settles each item from its `candidates` and extent under FR-290: unknown-backend, and more than one candidate with no named backend, settle `invalid-request`; an empty set settles `unsupported` with a warning; a single candidate settles through its negotiation arm. A request item without `candidates` refuses before consumption. | Test (TC-271) |
| FR-331-AC-5 | Two requests whose items differ only in `candidates` have different request identities, and candidates serialize in ascending identity order under every registration order. | Test (TC-271) |
| FR-331-AC-6 | A tool-absence `unsupported` result keeps the item's `supported` disposition, is the item's one terminal accounting record, and names the capability kind, backend and expected tool identity. | Test (TC-271) |
